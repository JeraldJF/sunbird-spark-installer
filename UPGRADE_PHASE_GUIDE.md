## Phase 1: Lock Reproducibility

**Status:** 🚨 DO TODAY | **Duration:** 30 min | **Risk:** 🟢 LOW | **Impact:** 🔴 CRITICAL

```
┌─────────────────────────────────────────────────────────────────┐
│  PHASE 1: Emergency Fix for Non-Reproducible Deployments       │
└─────────────────────────────────────────────────────────────────┘

WHAT'S BROKEN:
  tofu init -upgrade  ← Fetches LATEST provider versions
       ↓
    No consistency
       ↓
  Different versions each deployment

HOW WE FIX IT:
  1. Add required_version blocks (main.tf)
  2. Remove -upgrade from scripts
  3. Populate lock files
  4. Commit .opentofu.lock.hcl

RESULT:
  tofu init  ← Uses lock file (reproducible!)
       ↓
    Same versions always
       ↓
  Identical infrastructure each time
```

### Files to Create/Modify

```
opentofu/
├── azure/
│   └── template/
│       ├── main.tf          ← CREATE (new file)
│       ├── install.sh       ← MODIFY (remove -upgrade)
│       └── .opentofu.lock.hcl ← AUTO (generated by tofu init)
│
└── gcp/
    └── template/
        ├── main.tf          ← CREATE (new file)
        ├── install.sh       ← MODIFY (remove -upgrade)
        └── .opentofu.lock.hcl ← AUTO (generated by tofu init)

addons/
└── dial/
    └── opentofu/
        └── azure/
            └── storage/
                └── main.tf   ← MODIFY (align constraint 4.0.1 → 4.0)
```

### Step-by-Step

```
Step 1: Create Azure main.tf
  └─ Add terraform block with required_version and required_providers

Step 2: Create GCP main.tf
  └─ Add terraform block with required_version and required_providers

Step 3: Remove -upgrade from Azure install.sh
  └─ tofu init -upgrade  →  tofu init

Step 4: Remove -upgrade from GCP install.sh
  └─ tofu init -upgrade  →  tofu init

Step 5: Generate lock files
  ├─ cd opentofu/azure/template && tofu init
  └─ cd opentofu/gcp/template && tofu init

Step 6: Update DIAL addon
  └─ Change azurerm ~> 4.0.1  →  azurerm ~> 4.0

Step 7: Commit everything
  └─ git add . && git commit
```

### Success Criteria

```
✅ All 7 tasks completed
✅ Lock files committed to git
✅ No 'tofu plan' shows unexpected changes
✅ 'tofu init' runs without errors
```

### Parallel Work

All tasks can run in parallel. Estimated time:
- 1 person sequential: 30 minutes
- 2 people parallel: 20 minutes

### Changes Required

**GCP modules** (add terraform block):
```hcl
terraform {
  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 5.0"
    }
  }
}
```

**Azure keys module** (add terraform block):
```hcl
terraform {
  required_providers {
    tls = {
      source  = "hashicorp/tls"
      version = "~> 4.0"
    }
  }
}
```

**DIAL addon**:
```hcl
# Change from:
version = "~> 4.0.1"

# To:
version = "~> 4.0"
```

```

SOLUTION:
  ├─ Pin AKS to 1.33.6 (current version)
  ├─ Pin GKE to 1.33.0 (current version)
  └─ Document version policy

RESULT:
  ✅ Explicit K8s version in code
  ✅ No unintended version changes
  ✅ Control when K8s upgrades happen
  ✅ Version policy documented
```

### Files to Modify

```
Module Changes:
├── opentofu/azure/modules/aks/main.tf     ← ADD kubernetes_version variable
└── opentofu/gcp/modules/gke/main.tf       ← ADD kubernetes_version variable

Environment Values:
├── opentofu/azure/dev/terraform.tfvars       ← ADD kubernetes_version = "1.33.6"
├── opentofu/azure/staging/terraform.tfvars   ← ADD kubernetes_version = "1.33.6"
├── opentofu/azure/production/terraform.tfvars ← ADD kubernetes_version = "1.33.6"
├── opentofu/gcp/dev/terraform.tfvars         ← ADD kubernetes_version = "1.33.0"
├── opentofu/gcp/staging/terraform.tfvars     ← ADD kubernetes_version = "1.33.0"
└── opentofu/gcp/production/terraform.tfvars  ← ADD kubernetes_version = "1.33.0"

New Documentation:
└── docs/KUBERNETES_VERSION_POLICY.md       ← CREATE version policy
```

### Code Changes

**AKS Module** (add to main.tf):
```hcl
variable "kubernetes_version" {
  description = "Kubernetes version for AKS cluster"
  type        = string
  default     = "1.33.6"

  validation {
    condition     = can(regex("^1\\.(3[3-4]|35)", var.kubernetes_version))
    error_message = "Kubernetes version must be 1.33.x, 1.34.x, or 1.35.x"
  }
}

resource "azurerm_kubernetes_cluster" "main" {
  # ... existing config ...
  kubernetes_version = var.kubernetes_version
}
```

**GKE Module** (add to main.tf):
```hcl
variable "kubernetes_version" {
  description = "Kubernetes version for GKE cluster"
  type        = string
  default     = "1.33.0"
}

variable "release_channel" {
  description = "Release channel: REGULAR, STABLE, RAPID"
  type        = string
  default     = "REGULAR"
}

resource "google_container_cluster" "primary" {
  # ... existing config ...
  min_master_version = var.kubernetes_version
  release_channel {
    channel = var.release_channel
  }
}
```

### Validation

```bash

cd opentofu/azure/dev
tofu plan

# Should output: "No changes. Your infrastructure matches the configuration."
```

### Parallel Work

- AKS updates (create variable + update 3 environments): 25 minutes
- GKE updates (create variable + update 3 environments): 25 minutes
- Documentation: 10 minutes
- **Can all be done in parallel: 30 minutes total**

## Phase 4: Upgrade Kubernetes Clusters

**Status:** ⏳ IN 2 WEEKS | **Duration:** 4-6 hours per cluster | **Risk:** 🟠 MEDIUM | **Impact:** 🟢 HIGH

```
┌─────────────────────────────────────────────────────────────────┐
│  PHASE 4: Rolling Kubernetes Upgrades (1.33 → 1.34)            │
└─────────────────────────────────────────────────────────────────┘

TIMELINE:
  Week 1-2: Phases 1-3 stabilize in production
  Week 3: Upgrade dev cluster (1.33.6 → 1.34.0)
          Validate for 24 hours
  Week 4: Upgrade staging cluster (1.33.6 → 1.34.0)
          Validate for 8 hours
  Week 4: Upgrade production cluster (1.33.6 → 1.34.0)
          Validate for 24 hours

UPGRADE METHOD:
  Rolling update (no downtime)
  ├─ Master nodes upgrade first
  ├─ Worker nodes upgrade one at a time
  ├─ Pods automatically migrate to other nodes
  └─ Total time per cluster: 30-60 minutes
```

### Dev Cluster Upgrade

```
Step 1: Edit terraform.tfvars
  kubernetes_version = "1.33.6"  →  "1.34.0"

Step 2: Plan
  tofu plan
  → Review output

Step 3: Apply
  tofu apply
  → Watch Azure portal for progress
  → Should take 30-60 minutes

Step 4: Verify
  kubectl version --short
  kubectl get nodes -o wide
  kubectl get pods -A

Step 5: Validate (24 hours)
  ✅ All pods running
  ✅ Services responding
  ✅ No errors in logs
  ✅ Database connectivity working
  ✅ Flink jobs processing

Step 6: Approval
  Sign off before proceeding to staging
```

### Staging Cluster Upgrade

```
Same as dev cluster (step 1-6)
But validation time can be shorter (8 hours)
Since dev already proved it works
```

### Production Cluster Upgrade

```
CRITICAL: Schedule during maintenance window

Step 1: Backup
  ✅ Velero backup completed
  ✅ Backup verified restorable

Step 2: Plan
  kubernetes_version = "1.33.6"  →  "1.34.0"
  tofu plan

Step 3: Get Approval
  ✅ Security team
  ✅ Engineering manager
  ✅ On-call engineer

Step 4: Apply (DURING MAINTENANCE WINDOW)
  tofu apply
  → Monitor continuously
  → Have dashboards open

Step 5: Verify Immediately
  ✅ All nodes at 1.34.0
  ✅ All pods running
  ✅ No application errors

Step 6: Monitor (24 hours)
  ✅ Metrics normal
  ✅ No increased errors
  ✅ User experience normal
  ✅ Stakeholder approval

Step 7: Document
  ✅ Record lessons learned
  ✅ Update runbooks
  ✅ Celebrate success 🎉
```

### Success Criteria

```
✅ Dev cluster: 1.34.0 stable 24+ hours
✅ Staging cluster: 1.34.0 stable 8+ hours
✅ Production cluster: 1.34.0 stable 24+ hours
✅ Zero data loss
✅ Zero downtime (rolling upgrade)
✅ All workloads validated
```

### Rollback Plan

```
If something goes wrong:
  kubernetes_version = "1.34.0"  →  "1.33.6"
  tofu apply

  Wait 30-60 minutes for downgrade
  Verify cluster stability
```

## Decision Tree

### "Should I do Phase X today?"

```
Phase 1 (Lock Reproducibility)
  ├─ Is your code ever deployed twice with different infrastructure?
  │  ├─ YES → DO NOW (30 min, fixes critical issue)
  │  └─ NO → Skip (unlikely, do it anyway for safety)

Phase 2 (Standardize Providers)
  ├─ Do you have GCP clusters?
  │  ├─ YES → DO THIS WEEK (45 min)
  │  └─ NO → SKIP (not needed, but recommended)

Phase 3 (Pin K8s Versions)
  ├─ Do you want to control K8s upgrades?
  │  ├─ YES → DO THIS WEEK (1 hour)
  │  └─ NO → SKIP (K8s will auto-update)

Phase 4 (Upgrade K8s)
  ├─ Are you ready to upgrade clusters?
  │  ├─ YES → DO IN 2 WEEKS (need Phases 1-3 stable first)
  │  └─ NO → SKIP (can stay on 1.33.6)

Phase 5 (Long-term)
  ├─ Do you want repeatable, safe upgrades?
  │  ├─ YES → PLAN NOW, EXECUTE ONGOING
  │  └─ NO → SKIP (risk unplanned downgrades)
```
